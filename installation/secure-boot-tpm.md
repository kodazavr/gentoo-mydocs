# Безопасность: Secure Boot и TPM 2.0

Этот раздел описывает процесс настройки доверенной загрузки (Verified Boot) с использованием собственных ключей и аппаратного модуля TPM для автоматической расшифровки раздела LUKS.

> **Важно**: Secure Boot проверяет подписи доверенной загрузочной цепочки —
> неподписанный или подменённый компонент не пройдёт проверку. Автоматическая
> расшифровка через TPM зависит от выбранной PCR-политики: если измеряемое
> состояние на момент загрузки не совпало с состоянием на момент зачисления
> токена, вместо авторазблокировки система запросит пароль LUKS. Уровень
> защиты определяется выбранным набором PCR и конфигурацией загрузочной
> цепочки, а не самим фактом включения Secure Boot.

## 1. Подготовка UEFI (Setup Mode)

Перед генерацией ключей необходимо перевести прошивку материнской платы в режим, позволяющий записывать собственные ключи.

1. Зайдите в BIOS/UEFI (обычно клавиша F2 или Del).
2. Перейдите в раздел Security -> Secure Boot.
3. Найдите опцию удаления стандартных ключей (Microsoft) или перевода в Setup Mode (часто называется "Reset to Setup Mode" или "Custom Mode").
4. Убедитесь, что Secure Boot включен, но находится в режиме User Mode: Setup.
5. Сохраните настройки и загрузитесь в Gentoo.

## 2. Управление ключами через sbctl

Для работы с ключами используется утилита app-crypt/sbctl. Она автоматизирует создание и запись ключей в NVRAM материнской платы.

### Создание ключей

```bash
# Создание собственной иерархии ключей
doas sbctl create-keys
```

### Запись ключей в прошивку

Записываем свои ключи (и, при необходимости, ключи Microsoft для поддержки стороннего оборудования/Option ROM).

```bash
# Запись ключей в UEFI
doas sbctl enroll-keys -m
```

> **Примечание**: Флаг `-m` (Microsoft) рекомендуется для сохранения совместимости с видеокартами и прошивками других устройств.

### Подпись UKI

После записи ключей убедитесь, что ваш образ UKI (созданный через Dracut) подписан. В нашем конфиге 90-uki.conf для Dracut это происходит автоматически, но можно проверить вручную:

```bash
doas sbctl status
doas sbctl verify
```

## 3. Привязка LUKS к TPM 2.0 (systemd-cryptenroll)

Вместо ввода пароля при каждой загрузке мы используем systemd-cryptenroll для привязки ключа к регистрам PCR (Platform Configuration Registers) модуля TPM.

### Как выбирают PCR

Ключ, зачисленный через `systemd-cryptenroll`, отпирается автоматически, только если значения выбранных PCR в момент загрузки совпали с моментом зачисления. Часто используемые регистры:

- **PCR 0** — контроль прошивки (Core System Firmware);
- **PCR 2** — option ROM;
- **PCR 4** — загрузчик (для UKI — сам образ);
- **PCR 7** — состояние Secure Boot: политика, ключи, сертификаты;
- **PCR 8/12** — командная строка ядра и параметры загрузки.

Чем шире набор, тем строже политика — и тем чаще придётся перезачислять токен: любое изменение измеряемого содержимого (обновление BIOS, перезапись ключей Secure Boot, пересборка UKI со сменой cmdline) делает его недействительным.

Распространённый «строгий» вариант — `0+7`: разблокировка связывается и с прошивкой, и с состоянием Secure Boot.

> ⚠️ **Важный нюанс**: не предполагайте состав PCR по спецификации — прошивки измеряют в регистры больше канона (например, командную строку ядра в PCR 7 вместо 8/12). Перед фиксацией набора снимите слепки до и после типичных изменений: `tpm2_pcrread sha256:<N>`. Как находить фактический состав — в [troubleshooting: TPM2-анлок после пересборки UKI](../troubleshooting/luks-tpm2-unlock-after-uki-rebuild.md).

### Что проверено на эталонной машине

На ASUS ExpertBook B5402 выбран набор из одного **PCR 7**. Наблюдение: смена
cmdline 2026-09-14 совпала с PCR-mismatch и потерей авторазблокировки,
повторное зачисление восстановило её; в марте/апреле были сбои анлока,
причина которых не исследовалась. Гипотеза — одно из изменений загрузочной
цепочки влияет и на значение PCR 7; точный measurement path прошивки не
подтверждён: прямой before/after-замер `tpm2_pcrread sha256:7` для смены
cmdline не выполнялся. Токен перезачислен на PCR 7 и проверен реальной
загрузкой 2026-09-14. Хронология, диагностика и процедура перезачисления —
в [troubleshooting: TPM2-анлок после пересборки UKI](../troubleshooting/luks-tpm2-unlock-after-uki-rebuild.md).

Состояние на 2026-09-22: `sbctl status` — Setup Mode Disabled, Secure Boot
Enabled, vendor keys microsoft; `sbctl verify` — все присутствующие в ESP
образы подписаны (включая текущий UKI и systemd-boot). Автоподпись UKI — через
`uefi_secureboot_cert/key` в `/etc/dracut.conf.d/90-uki.conf`.

### Процесс привязки

Найдите ваш зашифрованный раздел (например, `/dev/nvme0n1p3`) и выполните привязку с выбранным набором PCR:

```bash
# Общий пример: PCR 0 + 7
doas systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=0+7 /dev/nvme0n1p3

# Набор, проверенный на эталонной машине asus-b5402: только PCR 7
doas systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/nvme0n1p3
```

> **Важно**: зачисление TPM-токена не удаляет парольный слот — пароль остаётся способом открыть раздел, если TPM сломается или PCR изменятся. После зачисления при следующей загрузке `systemd-cryptsetup` в initramfs (добавленном в Dracut) обратится к TPM, сверит выбранные PCR и отдаст ключ для расшифровки.

## 4. Финализация

1. Перезагрузитесь в BIOS.
2. Убедитесь, что Secure Boot активен и перешел из Setup Mode в User Mode (Deployed).
3. Загрузите систему. Теперь ввод пароля от LUKS не потребуется, если загрузка проходит в штатном режиме.
